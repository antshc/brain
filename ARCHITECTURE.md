# Brain Overview

A collection of GitHub Copilot agent plugins, skills, and Python tooling that automate coding workflows (issue triage, PR review, autonomous implementation) — organized as a flat plugin marketplace with shared Python modules synced into it at commit time.

## Context

See [CONTEXT.md](CONTEXT.md) for the shared language.

## Building blocks

### Codebase Structure

- `.githooks/pre-commit` — syncs modules into plugins/skills before each commit
- `.github/instructions/` — write-time authoring rules, auto-applied by `applyTo` glob
- `plugins/` — Copilot agent plugins, each with its own `plugin.json`, `skills/`, and optional `agents/`
- `skills/` — Copilot agent skills not tied to a specific plugin
- `tools/` — Python CLI tooling
  - `tools/src/modules/` — shared Python modules, source of truth
    - `tools/src/modules/github/` — GitHub domain + infrastructure (`domain/`, `features/`, `infrastructure/`, `shared/`), synced by `.githooks/pre-commit` into the plugin skill folders that consume it as a standalone script
  - `tools/src/afk/` — `afk` CLI tool (entry points registered in `pyproject.toml`'s `[project.scripts]`)
    - `tools/src/afk/features/` — one folder per AFK service (`cli.py` + `handler.py`), e.g. `fix_prs/`, `dev/`
  - `tools/tests/unit/` — unit tests mirroring `tools/src/`
  - `tools/tests/integration/` — integration tests
- `logs/` — runtime logs (daily JSON per repo)

## Architecture Decision Records

| Decision | Trigger condition | Summary |
|----------|-------------------|---------|

| [Crew agents own their workflows and use codebase instructions](docs/adr/crew-is-agnostic.md) | crew agent workspace behavior, `codey-*`/`chorey` run location, selecting which crew agent runs, adding a stack agent, `init-crew` copying stack instructions, per-stack `CODE`/`VERIFY` files, Chorey review gating, which agent outcome governs the loop, trusted `## HARNESS`/`## TASK` inputs | Each stack-specific Codey agent owns its implementation and verification flow in cwd and reads codebase `.github/instructions/`; Chorey reviews staged changes only after Codey reports complete, and Codey's report alone governs `ralph:dev`. |
| [wf plugin is operating-system-agnostic](docs/adr/wf-is-agnostic.md) | writing or reviewing a `wf` skill's command or script, adding a bash- or PowerShell-only snippet, a skill needing logic beyond a bare CLI invocation, cross-platform skill authoring | `wf` skills use bare cross-platform CLI invocations inline and move any logic beyond that into Python, never OS-specific shell syntax. |
| [Trigger-indexer is resource-agnostic](docs/adr/trigger-indexer-is-resource-agnostic.md) | changing the indexing skill, adding a new indexed table or record type, hardcoding table shape or location into the indexer | The indexer receives table and row metadata from callers, so any Trigger-condition table reuses generation, scan/match, and sync without a skill change. |
| [atl is MCP-first with Python-owned conversion](docs/adr/atl-is-mcp-first.md) | merging or splitting the Atlassian plugins, adding an `atl` skill, choosing between the Atlassian MCP and a Python/REST backend, Markdown-to-ADF or ADF-to-Markdown conversion, Atlassian API token handling, Confluence attachment or mermaid upload, naming a Jira or Confluence access skill | One `atl` plugin moves bytes through the Rovo MCP and shapes them in Python via `map-markdown-adf`; the API token is used only for what the MCP cannot do. |
| [explore-codebase is skill-agnostic](docs/adr/explore-codebase-is-skill-agnostic.md) | delegating a codebase lookup to a subagent, a skill naming its own lookup engine, passing a skill or prompt into exploration, changing what `explore-codebase` returns | `explore-codebase` owns subagent delegation and tool selection but no knowledge of the question, prompt, or skill it runs, returning the caller's own output shape unaltered. |
| [Crew agents use `include-custom-instructions: true` to load repository instructions](docs/adr/crew-agents-uses-instructions.md) | subagents missing repository instructions, `include-custom-instructions` frontmatter, crew agents loading `.instructions.md` files, a per-agent coding-convention gate, restating conventions in a subagent prompt | Crew agents set `include-custom-instructions: true` so subagents load the repository's unconditional and `applyTo`-scoped instruction files without an agent-authored gate. |

## Crosscutting Concepts

| Concept | Trigger condition | Default |
|---------|-------------------|---------|
| **[Resource Access Skill](docs/concepts/structure-resource-access-skill.md)** | a skill encapsulating access to a ticket tracker, docs backend, or other external infrastructure, vendor commands or IDs appearing in a caller, swapping the backend behind an existing skill, index-table read/write ownership, a new external API reached from more than one place | Put vendor-specific knowledge for one infrastructure category inside a single skill and let callers reach it through that skill's documented actions. |
| **[Ledger](docs/concepts/structure-ledger.md)** | session tracking of opened Concept/ADR/building-block records, grilling or domain-modeling session state, avoiding a duplicate index re-scan, a long session losing track of what was already validated, deciding where session-scoped state is persisted, re-scoping to a module already discussed | Persist session-scoped state via the memory tool under `/memories/session/`, created lazily on first write, and check it before re-opening or re-scanning anything. |
| **[Trigger Indexer](docs/concepts/structure-trigger-indexer.md)** | adding a new indexed table or row type, trigger phrases missing domain language, index rows drifting out of sync with their records, a caller re-implementing scan or match logic inline, deciding whether an indexed record applies to the current change, a blank Trigger condition cell, a hand-authored index table | Route trigger generation, scan/match, and row synchronization for any Trigger-condition table through the indexing skill, passing table and row metadata rather than re-implementing the logic in the caller. |
| **[Completeness Sweep](docs/concepts/ops-completeness-sweep.md)** | designing a skill's closing or completion step, declaring a task complete, reviewing whether a change covers every requirement, a change that compiles but may have missed a branch, deciding what a final pass should check, deferring an obligation | Close any task-completing skill with a sweep that maps each obligation to evidence and resolves the gaps as a fix, a question, or an explicit deferral — never silence. |
| **[Checklist-Driven Workflow](docs/concepts/structure-checklist-workflow.md)** | authoring a skill with a sequential multi-step procedure, a step that can fail and require returning to an earlier step, a task needing resumable progress tracking, progress that must survive a context reset, an agent drifting out of sequence, naming a checklist header | Embed a literal, fenced checklist the agent copies into its working notes whenever a procedure has three or more ordered steps, or whenever progress must survive a context reset. |
| **[Agent Design](docs/concepts/structure-agents-style.md)** | writing or reviewing an `.agent.md`, composing an agent from skills, a vague or generic persona description, an agent owning specialized complexity, an agent drifting into inconsistent behavior across invocations, deciding how autonomous an agent should be, an agent with no stated output format, declaring which files or areas an agent covers, a family of related agents, one agent overriding another's phase | Give an agent one concrete deliverable, a bounded scope, stated autonomy, explicit never-rules, and a literal output-format block; delegate every specialized procedure to a skill. |
| **[Instruction Robustness](docs/concepts/ops-instruction-robustness.md)** | writing agent instructions that are being restated instead of executed, a MUST treated as preference, an instruction ignored through an equivalent-looking shortcut, adding rationale to improve compliance, preventing reinterpretation or optimization around a rule, deciding whether to pair MUST with MUST NOT, defining behavior when a required action is unavailable | Write critical instructions as direct observable constraints: state the trigger and required behavior, forbid plausible substitutes, add a terse rationale for non-obvious constraints, close predictable optimization paths, and define the failure path. |
| **[Per-Repo Config Resolution](docs/concepts/ops-per-repo-config-resolution.md)** | a skill or agent reading per-repository configuration, adding a dotfile or convention folder under the Harness Repo Path, choosing between a fixed config path and a search, config lookup falling back to a second location, a config file holding a secret, deciding whether config is committed or gitignored, a component re-deriving a caller-supplied path, one config file per variant or stack, telling a shared config file from a per-variant one, consolidating several plugins' settings into one per-developer file, a settings file with one section per plugin, a credentials section, locating the harness anchor, resolver output exposing a secret, a script reading its own plugin's settings file, deriving a repository checkout path from its `owner/name`, a setting removed from the settings file because it can be derived, a settings file beside a repository-level skill, deriving the Harness Repo Path from a skill's own location, a setup skill copying a skill template and its settings file into the repository, gitignoring a file inside a committed skill folder, a missing or unparseable settings file | Resolve a per-repo config file at a fixed path under the Harness Repo Path, encoding any per-variant split in the filename rather than in a second lookup; keep each plugin's per-developer settings and credentials in its own gitignored file beside its repository-level skill, credentials read only by the script that uses them; derive a repository checkout path from the Harness Repo Path and the repository's name, never from the settings. |
| **[Skill-Owned Code](docs/concepts/structure-skill-owned-code.md)** | a skill needing a helper script, deciding where a skill's Python lives, adding a module to `tools/src/modules/`, adding a mapping to the pre-commit sync hook, two skills needing the same logic, placing a skill's tests, vendoring a library inside a skill, a skill importing another skill's code, a skill copying a script into the consumer's harness repository | Put a skill's Python and its tests inside the skill folder; promote to `tools/src/modules/` only once a second plugin needs the same code. |
| **[Skill Composition](docs/concepts/structure-skill-composition.md)** | splitting one skill into two, a procedure needed by more than one skill, an agent body restating a skill's steps, deciding whether a skill is model- or user-invoked, choosing what a new skill is responsible for, one skill reaching another skill's behaviour, a skill accumulating unrelated responsibilities, the same steps appearing in two skills, a family of related agents sharing a workflow, one agent extending or overriding another, an agent file pointing at another agent file, a skill running another skill inside a subagent, a skill naming the skills it can delegate to, deciding who owns lookups when one skill runs inside another, a delegated skill invoking its own delegator, a main skill whose behavior should grow through specialist skills, naming a `skillname-*` extension family, dynamically discovering matching skill families, a hardcoded list of specialists in a dispatcher | Give each skill one purpose; discover specialist extensions through a documented `skillname-*` family, and invoke their documented actions rather than duplicating or hardcoding their behavior. |
| **[Repository Adapter Skill](docs/concepts/structure-repository-adapter-skill.md)** | a repository-level skill generated to wrap a user-level skill, a setup skill scaffolding a per-repository adapter skill, `pub-<type>`-style generated skills, binding repository-specific data before invoking a shared workflow, a generated skill duplicating a user-level workflow instead of invoking it, deciding where a generated wrapper skill should live, required fields or keys pre-filled per repository, a setup skill discovering per-repository variants live | Generate a repository-level skill only as a thin adapter that resolves this repository's bound data and invokes the owning user-level skill's documented action — never a fork of its procedure. |
| **[Cross-Scope Skill Family](docs/concepts/structure-cross-scope-skill-family.md)** | an orchestrator skill discovering `skillname-*` extension members, a `skillname-*` family member added in a repository or user scope, cross-scope skill discovery, extending a shared orchestrator without editing the plugin that ships it, a locally added skill not being picked up by a dispatcher, `research-*`/`inspect-*`-style specialist discovery, scoping a skill roster scan to one plugin only | Scan the complete skill roster across every scope for a `skillname-*` family, and select a member by its description and compatibility — never hardcode the list or scope the scan to one plugin. |
| **[Improvement Flywheel](docs/concepts/ops-improvement-flywheel.md)** | an agent repeating a mistake a previous run already hit, deciding where a fix for agent behaviour is recorded, rewriting a skill for something a memory line would fix, session friction worth keeping, a recurring question the agent should not need to ask, a gotcha discovered mid-run, choosing between memory and a skill edit, an agent using the wrong tool or skipping a validation, a session ending with friction nothing has recorded, a document that misrouted the very run it was steering | Sweep the session's own context for observed failures before it closes, and route each to the cheapest tier that fixes it — a memory or gotcha line for a missing fact, a change to the skill, instruction, or agent body that misrouted the run for wrong routing or a missing guardrail. |
| **[Canary Rule Verification](docs/concepts/ops-canary-rule-verification.md)** | verifying whether an edited instructions, skill, or agent file is actually loaded, testing an `applyTo` glob match, doubting whether a disclosed reference file is being read, confirming a frontmatter or load-order change takes effect, a customization file edit with no visible effect, debugging why a rule isn't being followed, choosing between behavioral testing and static inspection for a customization change | Verify a load-bearing customization change with a temporary, obviously artificial canary rule that produces a visible marker in the agent's output, then remove it immediately. |
| **[CLI JSON Handoff](docs/concepts/str-cli-json-handoff.md)** | passing credentials or facts between two CLI scripts, one script consuming another's stdout, printing JSON to stdout, parsing subprocess stdout as JSON, choosing subprocess capture vs shell piping, secrets leaking into logs or stderr, a producer script mixing logs into its JSON output, inter-process data handoff between independently invoked scripts | Have the producer print a single JSON payload to stdout (logs/errors to stderr) and have the consumer parse it via `subprocess.run(..., check=True)`, reserving shell piping for ad hoc wrapper composition. |
| **[Open-Question Marker](docs/concepts/str-open-question-marker.md)** | drafting an artifact with a choice the gathered facts don't settle, deciding whether to guess or ask, a draft carrying an unmarked assumption, closing a draft while a choice is still open, writing a Review or confirmation step for a drafted document, batching open choices into one question round, re-verifying a draft after the user answers, inline `❓` markers | Mark every fact-unsettled choice `❓` inline with the agent's own safest/cheapest default, then resolve every `❓` in one `questioning`-style round before the draft counts as final. |
