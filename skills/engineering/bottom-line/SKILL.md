# Bottom line

A bottom line answers three questions, in order, in 1–3 sentences:

1. **What did we find?** — the finding.
2. **So what?** — why it matters.
3. **Now what?** — the recommended action.

## Write it

1. State the finding as the answer itself, not the path to it. Done when a reader who stops here knows the conclusion, not the investigation.
2. State why it matters — the consequence for the decision at hand (cost, risk, capability unlocked). Done when the finding is tied to an outcome.
3. State the recommended action as an imperative, not a hedge. Done when the reader knows what to do next, not just what to consider.
4. Cut everything else — evidence, alternatives, context — into the sections below the bottom line. Done when the bottom line alone still reads as complete.

### Example

> Git CLI is the preferred approach because it provides full Git functionality without an additional abstraction dependency. GitPython simplifies basic operations but introduces limitations for advanced worktree operations. Use Git CLI behind a dedicated Git facade.

## Rules

- Decision-oriented, not information-oriented: a reader acting on the bottom line alone makes the right call.
- Lead with the conclusion; never with the setup or method.
- No hedging ("it depends", "could potentially") unless the recommendation is genuinely conditional — then state the condition as part of the action.
- Not an **executive summary**: a summary spans paragraphs and covers findings, evidence, and conclusions; a bottom line is one decision, stated once.

## In a full research document

Place the bottom line first, under its own heading, before any findings or evidence. Use [`templates/research-structure.md`](templates/research-structure.md) for the surrounding document shape.
