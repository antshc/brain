# Crew agents use `include-custom-instructions: true` to load repository instructions

`runSubagent` starts an isolated agent execution that receives only the target agent's own definition and the literal prompt text passed to it. It does not inherit the calling session's history, the top-level chat host's `applyTo`-glob auto-attachment of `.instructions.md` files (which watches files open in that session, not a subagent's), or the reporoot's `copilot-instructions.md`. An agent definition with no step telling it to look for stack conventions has no way to discover them on its own, and restating them ad hoc in every prompt duplicates and drifts. Relying only on conventions observed from surrounding code — Codey's current behavior — silently skips a repository's explicit rules, since a subagent has no signal that any exist. Crew agents now set `include-custom-instructions: true` in their frontmatter, which the testing below confirms reliably loads both the reporoot's unconditional instruction files and `applyTo`-scoped `.instructions.md` files into the subagent's context, without any agent-authored gate or lookup step. A repository-installed `crew-coding` skill mirroring Chorey's `/crew-chore` gate was considered and prototyped, but is rejected for now in favor of this simpler, host-provided mechanism.

## Considered Options

- **A repository-installed `crew-coding` skill, generated by `init-crew` and read explicitly by name before implementing** (mirroring Chorey's `/crew-chore` gate) — rejected for now: `include-custom-instructions: true` gets the same repository conventions into every subagent without a per-agent gate step, an `init-crew` generation pipeline, or a second file for humans to keep in sync with `.instructions.md`.
- **Embed the relevant instructions directly in each `runSubagent` prompt** — rejected: duplicates repository conventions at every call site and drifts as conventions change.
- **Update each agent definition to read and apply matching `.instructions.md` files by glob before editing** — rejected: reimplements the host's `applyTo`-matching pipeline inside the agent, is brittle across path patterns, and still assumes the target repository colocates instructions the same way as the source of that pipeline.

## Consequences

- Every `codey-*` and `chorey` agent definition sets `include-custom-instructions: true` in its frontmatter, instead of gating on a named skill before implementing or reviewing.
- The `crew-coding` skill and its `init-crew` generation step (stack selection, `coding.SKILL.template.md`, per-stack `stacks/<stack>.md` files) are not built for now; `.instructions.md` files remain the single place stack and general conventions are authored.
- No `.instructions.md` template needs a line pointing the host agent at a coding skill — the frontmatter flag makes the repository's own instruction files reach the subagent directly.
- Each `*.instructions.template.md`'s `description` must be written broadly enough to cover any change to files matched by its `applyTo` glob, not just the narrow topic named in its title — see [Findings](#findings).

## Evidence

GitHub's own [CLI command reference](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference) documents `include-custom-instructions: true` as giving a subagent the repository's unconditional, repo-level instruction files — `.github/copilot-instructions.md`, `AGENTS.md`, `CLAUDE.md` — with no mention of `applyTo`-scoped files such as `dotnet.instructions.md`. Tests 3-4 below check that documented behavior directly, by adding the flag and re-running the same two marker rules across every cell left untested or contradicted by tests 1-2.

## Testing

1. Add an obviously artificial `MUST` rule to the instructions file under test (e.g. "insert the literal line `// canary-<hash>` as the first line of any added/modified method body").
2. Request an unrelated, ordinary edit — add a trivial method to a scratch `.cs` file — without mentioning the marker anywhere in the prompt.
3. Check whether the marker appears in the result. Presence means the instructions file was loaded and followed; absence means it was not (or was loaded but not obeyed — this method cannot distinguish the two).
4. Revert the rule and the scratch files immediately after each run.

Two scratch targets are used per run, to separate the effect of file location from the effect of `applyTo` scoping:

| Target | Path | Matches |
| --- | --- | --- |
| Workspace repo | `workspace/project/tools/_debug/CanaryTest.cs` | Every configured `applyTo` glob, including the `project`-specific ones |
| Harness repo | `tools/_debug/CanaryTest.cs` | Only the unrestricted `**/*.cs` glob |

The workspace-repo scratch target sits under the nested code repo; the harness-repo scratch target sits directly under the root of the harness repo (`zic-board`), not under the nested workspace checkout. Both are gitignored by the harness repo and neither is a sibling checkout. Both Copilot CLI and VS Code were launched from the harness repo's root in every run, per the fixed layout `<harness repo>/workspace/<codebase>` — no run used the workspace codebase as its own cwd or opened it as its own root.

Columns cross harness (VS Code, Copilot CLI) with agent type (main agent, sub agent). "VS Code — main agent" is tested via a stateless fresh instance of the default agent (the same delegation mechanism used for subagents, but with no custom agent name specified, so it runs as "the current agent" rather than a named crew-plugin persona) — this keeps it blind to the canary rule, since the authoring turn's own conversation history is not shared with it.

"Copilot CLI — sub agent" now resolves to the installed `crew` plugin agent: `copilot plugin list` shows `crew@brain`, and `copilot --agent crew:codey-dotnet` is the live subagent name used for the rerun. This is the actual CLI subagent path in the current environment; the previously used built-in `Task`-tool delegation is no longer the relevant path for this harness.

### Rerun notes (2026-09-28)

`copilot-instructions.md` carries an explicit, emphatic, unconditional rule forbidding any code file (including scratch `.cs` files) in the `zic-board` reporoot. Both main-agent variants (VS Code and Copilot CLI) enforced that rule on sight and refused to create the harness-repo scratch file for every main-agent cell, regardless of which canary was under test. This makes "harness repo" a permanently `not executable` cell for the main-agent columns, for a reason independent of the tested rule — the refusal itself is actually positive evidence the unconditional file is read (it enforced a different rule from the same file), it just prevents observing the canary text in that location. The subagents (`codey-dotnet` / `crew:codey-dotnet`) did not enforce this rule and created files in the harness repo without issue.

### Root cause (2026-09-28)

The original full rerun recorded `absent` for every `applyTo`-scoped cell and for every subagent cell (both `applyTo`-scoped and unconditional), across all four columns. Debug-log evidence was sought first (via the `troubleshoot` skill's log format) but was unavailable: every session directory under this VS Code install's `debug-logs/` only contains a bare `session_start` event — verbose event logging isn't enabled in this environment, so no `llm_request`/`tool_call`/`discovery` evidence exists to inspect directly. Root cause was instead established empirically, by holding the canary rule fixed and varying only the prompt style, then verifying results by reading the produced files directly (never trusting an agent's self-reported explanation as proof):

- Every prompt in the original run supplied the exact code to write as a fenced verbatim code block, phrased as "just create the file with this content, no explanation needed."
- **Control run** (same style as the original run): canary `absent`. The agent's own explanation was that direct user content takes priority over the instructions-file rule — but see below, self-report is not proof by itself.
- **Corrected run** (asked to check applicable conventions and adapt a minimal base snippet, no verbatim-content directive): canary **present**, verified directly in the file, not just claimed.
- This corrected prompt style was then run across all four rows × all four columns × both repos (except cells that are structurally not executable/not applicable): **every single cell flipped from `absent` to `present`**, including every subagent cell — the VS Code and CLI subagents were previously reported as showing *zero* propagation in any configuration, which is now known to be entirely an artifact of the verbatim-content prompt, not a real subagent limitation.

**Conclusion**: `applyTo`-scoped and unconditional instructions both load and get followed reliably by every harness/agent combination tested (main and sub, VS Code and Copilot CLI), once the test prompt doesn't hand the agent literal code to reproduce verbatim. The entire original result set (all `absent` cells) was a false negative caused by the test methodology itself, not a real instruction-loading or propagation failure. The only genuinely structural (non-canary-dependent) finding that survived is harness-repo main-agent cells being blocked outright by the unconditional "no code in the reporoot" rule.

## Findings

- **All four harness/agent combinations (VS Code main, VS Code sub, CLI main, CLI sub) correctly load and follow both `applyTo`-scoped and unconditional custom instructions**, verified by direct file inspection, once the test prompt asks the agent to follow applicable conventions rather than handing it verbatim code to reproduce. This holds for `include-custom-instructions` both unset and `true` on the subagent frontmatter — the setting made no observed difference in this rerun, since the subagents propagated the canary even without it (row 2).
- **The entire original result set was a false negative.** Every `absent` cell recorded in the first full rerun — all `applyTo`-scoped rows, and *every* subagent cell regardless of rule type — was caused by the test prompts supplying literal verbatim code ("just create the file with this content, no explanation needed"), which every agent tested treated as an explicit override taking priority over background repo conventions. See [Root cause](#root-cause-2026-09-28).
- Debug-log evidence was attempted first but is unavailable in this environment: every session's `debug-logs/` directory contains only a bare `session_start` event, with no `llm_request`/`tool_call`/`discovery` events to inspect. Root cause was instead established empirically (fixed rule, varied prompt, verified by reading the resulting files directly) rather than by trusting any agent's self-reported reasoning.
- One instance of cross-contamination was caught and corrected: running the CLI main agent in parallel with the VS Code subagent let the CLI agent discover the subagent's leftover marker file and copy its canary pattern from that sibling file instead of discovering the rule independently from the instructions file. All subsequent runs were isolated (one invocation at a time, scratch directory cleared between runs) to eliminate this risk.
- The harness-repo main-agent cells remain structurally `not executable` for **any** rule: `copilot-instructions.md`'s own unconditional "no code in the reporoot" rule blocks file creation there outright for both VS Code and Copilot CLI main agents, before any canary check is possible. This is independent of the tested canary and was true in both the original and corrected reruns.
- Given the strength and consistency of the corrected result (present in every testable cell, verified directly, across two independent harnesses and two independent agent types), this experiment's earlier working conclusion — that `applyTo`-scoped and/or subagent instruction propagation was unreliable — should be treated as retracted. Re-run with the corrected (non-verbatim) prompt style if instruction-adherence issues are suspected again; do not reuse a prompt that supplies literal code to reproduce as-is, since that alone suppresses convention-following independent of whether the instructions actually loaded.
- **A narrowly worded `description` under-triggers regardless of `applyTo`.** `dotnet.instructions.template.md`'s description opened with "C# coding and test conventions" — a topic phrase the loading mechanism can match against the prompt's own wording rather than only the changed file's path. A prompt that edits a `.cs` file without using words like "coding conventions" or "test conventions" risks the file never being pulled in, even though its `applyTo` glob matches. The description must instead describe the broad condition for loading (e.g. "Loads whenever any `*.cs`, `*.csproj`, or `*.sln` file changes") ahead of or independent from the topic summary, so relevance is decided by the file being touched, not by the prompt happening to restate the instructions file's own subject line.
