# Crew is run-location- and technology-agnostic
<!-- agent instruction: the file track all crew plugin adrs using the bullets-->
- **OS agnostic** `crew` skills and agents must not embed OS-specific shell syntax (bash-only or PowerShell-only) in their commands or helper scripts. Wherever a skill needs logic beyond a bare cross-platform CLI invocation (e.g. `gh`, `git`), that logic is written in Python so the same instruction runs unmodified on Linux, macOS, and Windows, instead of asking the agent to pick and maintain a per-OS variant.
- **Run-location-agnostic**: Crew agents execute code, Git, build, test, and exploration commands in the directory from which they were launched and do not change directories to interpret a worktree path. `WORKTREE_PATH` is not part of an agent's prompt, arguments, status output, or documentation. An agent does not need to know whether its directory is a worktree, a repository root, or another valid workspace; callers establish the execution location before invocation.
- **Technology-agnostic**: the agents (`codey`, renamed from Droid, itself renamed from Csdroid; and `chorey`) and their `crew-*` skills carry no language- or toolchain-specific knowledge either: no hardcoded build/test commands, project-file conventions, or language names in the agents or skill prose.
- **Per-repo resolution**: agents resolve their per-repo `CODE.md`, `VERIFY.md`, `CHORE.md`, and `GOTCHAS.md` files at `$HARNESS_REPO_PATH/.crew/<FILE>`, where `HARNESS_REPO_PATH` is supplied by the caller in a trusted `## HARNESS` prompt section. An agent performs no discovery and no cwd-first lookup: a supplied-but-invalid path (not absolute, contains `..`, or a non-existent directory) stops the agent as blocked, and it falls back to cwd only when no path is supplied. `.crew/` is the single location checked — there is no `.droid/` read-fallback, and nothing migrates one: `setup-crew` scaffolds fresh installations only, and renaming an existing `.droid/` is a manual step. All technology specifics — style, build/verify commands, layer conventions, review rules — live only in these per-repo files.
- **Fallback discovery**: when `VERIFY.md` is absent, `crew-feedback`'s fallback discovers the toolchain by reading the repo's own `README.md` and exploring its project files, instead of falling back to a specific language's tooling.
- **Two agents, one owner of the outcome**: `codey` implements the task; `chorey` reviews the resulting change set — a checkpoint commit inside the loop, uncommitted work standalone — for behavior-preserving maintainability refactors. Codey's five-field report alone governs `ralph:dev`'s distill, commit, and issue-handling steps — Chorey's report is informational and reaches only its own follow-up commit body, never Codey's `STATUS`. Codey owns the implementation reasoning that feeds the spec's Implementation Decisions; a refactor log is not an implementation decision.
- **Chorey is gated and self-reverting**: Chorey runs only when Codey reports `STATUS: complete`, because refactoring unverified or broken code cannot preserve behavior that was never established. Inside `ralph:dev`'s loop, Codey's result is committed as a checkpoint *before* Chorey runs, and that commit is passed to Chorey as a trusted `BASELINE_COMMIT`; Chorey reviews the change it introduced and, when its own verification cannot pass, discards its own refactors with a git-native rollback against that commit (`git checkout <BASELINE_COMMIT> -- <file>`) rather than a manual content snapshot, reporting them as findings instead of leaving a red tree behind a closed issue. Standalone `to-chorey` supplies no `BASELINE_COMMIT` and keeps reviewing uncommitted work with the original manual-snapshot revert, since it has no guaranteed prior commit to roll back to. A kept Chorey cleanup lands as its own follow-up commit, distinct from Codey's checkpoint.
- **Roster is named, internals are not**: `ralph:dev` names `codey` and `chorey` literally — falling back to a general-purpose agent when `codey` is unavailable, and skipping the review stage when `chorey` is. What it never assumes is an agent's internals or toolchain. Any substituted or skipped agent still yields a five-field report, synthesized by `ralph:dev` when the agent cannot produce one, so downstream steps never read a missing `STATUS`.
- **Entry points mirror the roster**: `to-codey` and `to-chorey` each invoke exactly one agent in the invocation directory. Orchestration of the pair lives only in `ralph:dev`, so the gate, the fallback, and the outcome-governance rule exist in one place.

## Considered Options

- **Keep the agent C#-specific** (status quo before this decision) — rejected: the `csdroid` name and the `droid-feedback` fallback's hardcoded `dotnet build`/`dotnet test`/`.csproj` walk-up made the harness unusable for non-C# repos and misstated the design intent every time someone read the agent's own description.
- **One agent that implements and tidies in a single pass** — rejected: a reviewer that authored the code it reviews has no independent baseline, and the "did the task succeed?" and "is the result maintainable?" questions then share one `STATUS`, so a failed cleanup and a failed implementation become indistinguishable.
- **Merge the two reports, or let Chorey's replace Codey's** — rejected: merging makes `ralph:dev` arbitrate field-by-field ownership on every run, and replacing loses the implementation SUMMARY the spec update depends on. The self-reverting gate reaches the same safety with one rule instead of four.
- **Let Chorey's `partial` escalate to `hitl`** — rejected: it reintroduces Chorey into outcome governance through a single field, contradicting the informational-only rule, for a case that self-reverting already prevents.
- **Sibling `CHORE.md` inside the skill folder** (the reference implementation's model) — rejected: a file living in the plugin is shared by every repo the plugin is installed into, which is the opposite of per-repo resolution.
- **`.crew/` with a `.droid/` read-fallback** — rejected: it reinstates the second lookup path that per-repo resolution exists to forbid, and its silent-degradation failure mode (no error, no conventions) means nobody ever notices they should migrate.
