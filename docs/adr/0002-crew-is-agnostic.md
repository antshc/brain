# Crew is run-location-agnostic and technology lives in stack deltas
<!-- agent instruction: the file track all crew plugin adrs using the bullets-->
- **OS agnostic** `crew` skills and agents must not embed OS-specific shell syntax (bash-only or PowerShell-only) in their commands or helper scripts. A step prefers a bare, pure cross-platform CLI invocation (e.g. `gh`, `git`) written inline in the instruction; only once the logic exceeds a single pure command — branching, parsing, multi-step state — is it moved to a Python script, so the same instruction runs unmodified on Linux, macOS, and Windows, instead of asking the agent to pick and maintain a per-OS variant.
- **Run-location-agnostic**: Crew agents execute code, Git, build, test, and exploration commands in the directory from which they were launched and do not change directories to interpret a worktree path. `WORKTREE_PATH` is not part of an agent's prompt, arguments, status output, or documentation. An agent does not need to know whether its directory is a worktree, a repository root, or another valid workspace; callers establish the execution location before invocation.
- **Technology lives in stack deltas**: the base agents (`codey`, renamed from Droid, itself renamed from Csdroid; and `chorey`) and their `crew-*` skills carry no language- or toolchain-specific knowledge: no hardcoded build/test commands, project-file conventions, or language names. Technology enters through **stack delta agents** — `codey-py`, `codey-dotnet`, `codey-ai` — each of which is frontmatter, a declared scope, and only the phases it overrides. A delta carries stack-level, project-agnostic knowledge (Python's exception-type hazard, .NET's `.csproj` shape); it never carries one repo's paths, commands, or layout, which stay in the per-repo files. `chorey` has no deltas: its workflow is stack-invariant, so only its rules vary, per stack, in `CHORE-<stack>.md`.
- **The base is a skill, not a parent file**: shared agent workflow lives in `crew-codey-flow` and `crew-chorey-flow`, which every agent reaches by name. An agent body is frontmatter plus a flow-skill invocation plus its own overrides — no agent file points at another agent file, because agent frontmatter carries only `name`/`description` and no agent can know its own install path. Codey and Chorey get separate flow skills rather than one: their INPUT, failure routing, and status vocabulary differ, and a single base would switch on its caller.
- **Per-repo resolution**: agents resolve their per-repo files at `$HARNESS_REPO_PATH/.crew/`, where `HARNESS_REPO_PATH` is supplied by the caller in a trusted `## HARNESS` prompt section. Files are named for their purpose and suffixed with the stack that owns them — `CODE-<stack>.md`, `VERIFY-<stack>.md`, `CHORE-<stack>.md` — while an unsuffixed name means shared across every stack, which is why `GOTCHAS.md` carries no suffix. A stack's file is resolved by exactly one name: a missing `CODE-py.md` is absent, never a reason to read `CODE.md`. An agent performs no discovery and no cwd-first lookup: a supplied-but-invalid path (not absolute, contains `..`, or a non-existent directory) stops the agent as blocked, and it falls back to cwd only when no path is supplied. `.crew/` is the single location checked — there is no `.droid/` read-fallback, and nothing migrates one: `setup-crew` scaffolds fresh installations only, and renaming an existing `.droid/` is a manual step. All repo specifics — style, build/verify commands, layer conventions, review rules — live only in these per-repo files.
- **Scoping is VERIFY's job; verifying at all is the skill's**: `VERIFY-<stack>.md` owns the file-to-Module walk-up, the Module-to-seam mapping, and every command, in its own stack's vocabulary. `crew-feedback` keeps only what no stack changes: collecting the change set from git, and the failure policy. When no `VERIFY` file resolves, the fallback discovers the toolchain by reading the repo's own `README.md` and exploring its project files, then runs it **unscoped** across the repo and says so in NOTES — slower, never silent. A missing `VERIFY` costs time, not safety, because `STATUS: complete` must never mean "I edited some files".
- **Two agents, one owner of the outcome**: `codey` implements the task; `chorey` reviews the resulting change set — a checkpoint commit inside the loop, uncommitted work standalone — for behavior-preserving maintainability refactors. Codey's five-field report alone governs `ralph:dev`'s distill, commit, and issue-handling steps — Chorey's report is informational and reaches only its own follow-up commit body, never Codey's `STATUS`. Codey owns the implementation reasoning that feeds the spec's Implementation Decisions; a refactor log is not an implementation decision.
- **Chorey is gated and self-reverting**: Chorey runs only when Codey reports `STATUS: complete`, because refactoring unverified or broken code cannot preserve behavior that was never established. It maps the change set's files to stacks through `crew-select` and applies each matched stack's `CHORE-<stack>.md` to that stack's files. Inside `ralph:dev`'s loop, Codey's result is committed as a checkpoint *before* Chorey runs, and that commit is passed to Chorey as a trusted `BASELINE_COMMIT`; Chorey reviews the change it introduced and, when its own verification cannot pass, discards its own refactors with a git-native rollback against that commit (`git checkout <BASELINE_COMMIT> -- <file>`) rather than a manual content snapshot, reporting them as findings instead of leaving a red tree behind a closed issue. Standalone `to-chorey` supplies no `BASELINE_COMMIT` and keeps reviewing uncommitted work with the original manual-snapshot revert, since it has no guaranteed prior commit to roll back to. A kept Chorey cleanup lands as its own follow-up commit, distinct from Codey's checkpoint.
- **Selection is a skill, and the vocabulary is closed**: `crew-select` owns the match — task text before the work exists, changed files after it does — and returns the stack(s) it resolves to. `ralph:dev`, `to-codey`, and `to-chorey` all invoke it rather than each carrying a copy of the rule. No stack matches → base `codey`, resolving no per-stack files, which is already its documented behaviour when they are absent. Two or more match → the primary stack selects the agent body, but **every** matching stack still contributes its `CODE` and `VERIFY`: choosing the wrong body is inert, while dropping a stack's verification ships unchecked work behind a green `STATUS`. A stack exists only where an agent ships for it, so `setup-crew` offers the shipped roster and never scaffolds a `CODE-go.md` that nothing would ever read.
- **Roster is named, internals are not**: `ralph:dev` names the crew literally — falling back to a general-purpose agent when the selected `codey` is unavailable, and skipping the review stage when `chorey` is. Agent-unavailable and no-stack-match are different failures with different answers: the first substitutes an agent, the second selects the base one. What `ralph:dev` never assumes is an agent's internals or toolchain. Any substituted or skipped agent still yields a five-field report, synthesized by `ralph:dev` when the agent cannot produce one, so downstream steps never read a missing `STATUS`.
- **Entry points mirror the roster**: `to-codey` and `to-chorey` each invoke exactly one agent in the invocation directory, the one `crew-select` named. Orchestration of the pair lives only in `ralph:dev`, so the gate, the fallback, and the outcome-governance rule exist in one place.

## Considered Options

- **Keep the agent C#-specific** (status quo before this decision) — rejected: the `csdroid` name and the `droid-feedback` fallback's hardcoded `dotnet build`/`dotnet test`/`.csproj` walk-up made the harness unusable for non-C# repos and misstated the design intent every time someone read the agent's own description.
- **One agent that implements and tidies in a single pass** — rejected: a reviewer that authored the code it reviews has no independent baseline, and the "did the task succeed?" and "is the result maintainable?" questions then share one `STATUS`, so a failed cleanup and a failed implementation become indistinguishable.
- **Merge the two reports, or let Chorey's replace Codey's** — rejected: merging makes `ralph:dev` arbitrate field-by-field ownership on every run, and replacing loses the implementation SUMMARY the spec update depends on. The self-reverting gate reaches the same safety with one rule instead of four.
- **Let Chorey's `partial` escalate to `hitl`** — rejected: it reintroduces Chorey into outcome governance through a single field, contradicting the informational-only rule, for a case that self-reverting already prevents.
- **Sibling `CHORE.md` inside the skill folder** (the reference implementation's model) — rejected: a file living in the plugin is shared by every repo the plugin is installed into, which is the opposite of per-repo resolution.
- **`.crew/` with a `.droid/` read-fallback** — rejected: it reinstates the second lookup path that per-repo resolution exists to forbid, and its silent-degradation failure mode (no error, no conventions) means nobody ever notices they should migrate.
- **Stack agents as standalone copies of `codey`, carrying a repo's own rules** — rejected: the copies drift apart on every base change, and a repo's paths and commands shipped in a plugin become one project's opinions imposed on every other repo that installs it. A delta carries only what is true of the stack anywhere.
- **Inheritance by file pointer between agent files** (`codey-py` reads the sibling `codey.agent.md`) — rejected: it reads like inheritance but has no addressing mechanism behind it, since agent frontmatter carries only `name`/`description` and the install path is unknowable to the agent. The only way to find the parent is the unbounded filesystem search the hard rules forbid.
- **One flow skill serving both Codey and Chorey** — rejected: their INPUT, failure routing, and status vocabulary differ, so the shared skill would branch on which agent invoked it — worse than two skills that each read straight through.
- **`chorey-<stack>` deltas** — rejected: Chorey's workflow is identical for every stack, so a delta would override nothing and be a filename wearing an agent's extension. Only its rules vary, and those already live in a per-repo file.
- **Per-stack subfolders (`.crew/py/CODE.md`)** — rejected in favour of suffixes: the folder buys nothing the filename doesn't, and it makes "shared across stacks" a position in a tree rather than a visible property of the name.
- **One file per agent per stack (`.crew/codey-py.md`) merging CODE and VERIFY** — rejected: the two are read by different skills at different phases, so each reader would load a file half of which it must ignore, and naming per-repo files after agents re-couples them to a roster that has already been renamed twice.
- **An open stack vocabulary, letting a repo declare a stack no agent ships for** — rejected: the resulting `CODE-go.md` is read by nothing, failing silently rather than loudly. The value of a stack is its delta; a stack without one is a suffix.
- **No verification when a stack has no `VERIFY` file** — rejected: it makes `STATUS: complete` mean "files were edited", and `ralph:dev` closes issues on that field.
