- A local `copilot plugin marketplace add` registers under the name in the target `marketplace.json`'s `"name"` field, not the `add` command's argument — testing a worktree's marketplace changes against the real `brain` marketplace name collides; temporarily rename the field for the test, then revert it before finishing.
- When grepping this repo for a retired capability/agent name after a rename, exclude `docs/adr/*` (decision history and rejected-options prose intentionally retain the old name) and `CONTEXT.md`'s `_Avoid_:` glossary lines (they intentionally name the old term as guidance).
- When operating in a worktree checkout that is separate from `HARNESS_REPO_PATH`, the bash tool's default cwd is neither — always `cd` into the intended directory explicitly at the start of every command rather than assuming persistence across calls. This also applies to file-editing tools that take absolute paths (create_file, replace_string_in_file, etc.): build every target path from the invocation cwd, never from `HARNESS_REPO_PATH`, when the two differ — verify with `git rev-parse --show-toplevel` before the first file write if unsure, and re-verify `git status --porcelain` in `HARNESS_REPO_PATH` afterward to confirm no stray edits landed there. Workspace-bound search tools (grep_search, file_search, semantic_search) ignore both cwd and `HARNESS_REPO_PATH` — they always scan the editor's open workspace folder, so results silently come from the wrong checkout when reviewing a worktree; use `grep`/`find` inside an explicit `cd` instead, and reserve `read_file`/absolute-path tools (which do honor the given path) for targeted reads.
- When a task scopes a `python3`→`python` rename to "invocation instruction text" only (e.g. resolve-harness, fix), leave each script's own `#!/usr/bin/env python3` shebang and internal `Usage: python3 <script>` docstrings untouched — those are script internals, not the calling skill's invocation text.
- When adding a new `.githooks/pre-commit` `sync_module` mapping (module → skill `scripts/` folder), Codey never commits, so the hook never fires this session — manually run the equivalent `rsync -a --delete <src>/ <dest>/` now so the synced copy exists on disk and is included in the uncommitted diff left for `to-commit`.
- When a new synced Python module's skill-folder destination directory name differs from the module's own name under `tools/src/modules/` (e.g. `github_tracker/` → `.../scripts/`), each entry-point script must resolve sibling package imports dynamically via `_SCRIPT_DIR.name` + `importlib` (like `git_worktree/create_worktree.py`), not hardcoded package-name imports (like `github/fetch_issues.py`, which only works because its synced destination folder is also named `github`).
- When deciding whether to extend an existing shared `tools/src/modules/` module vs. creating a new one, check `.githooks/pre-commit`'s `sync_module` mappings first — if the existing module already syncs into an unrelated skill folder, adding new code there bloats that skill's footprint; prefer a new self-contained module when the concerns genuinely differ (e.g. `github`'s read-only GraphQL vs. the new `github_tracker`'s write-oriented `gh` CLI ops).
- When a task requires an "identical stdout contract" with a bash script being replaced, verify exact spacing byte-for-byte with `cat -A` (or equivalent) rather than eyeballing — e.g. `create-labels.sh`'s `echo "exists:  $name"` has two spaces vs. `echo "created: $name"`'s one.
- When a Markdown output template contains fenced code examples, wrap the template in a longer fence than its examples and verify both opening/closing counts after patching — a broad fence replacement can close the outer template at the first inner example.
- When changed files are untracked, `git diff HEAD` and `git diff --check` omit them — use `git diff --no-index /dev/null <file>` to review them without staging user work.
- Direct Codey invocations must place the implementation request under a trusted `## TASK` heading — shorthand such as `implement` cannot inherit a task from conversation or session memory and is blocked before implementation.
- Skills with `context: fork` produce editor errors when `github.copilot.chat.skillTool.enabled` is disabled — omit `context` unless the plugin explicitly requires and enables that tool.
- When `apply_patch` reports a successful file deletion, verify the path is absent immediately — if repeated `Delete File` patches leave it intact, remove only that exact file and its empty directory with scoped filesystem commands.
- When a skill instructs the agent to post a `gh api graphql` body that it composes at runtime (review replies, issue bodies), specify `-F body=@<file>` and have the skill write the file first — inline quoting and heredocs inside `$(...)` break on backticks and newlines; verified against `gh` 2.92 (`-F key=value` accepts `@<path>`/`@-`).
- When copying `ingest-nuget-package`'s "Skill base directory" sentence into a new skill, drop its hardcoded `<reporoot>/.github/skills/<name>/` path — skills installed via `gh skill install` live elsewhere, so word it as "the directory holding this `SKILL.md`" and keep the "never via a bare relative link" clause.
- When reviewing skill-owned Python (Concept 0009) for cleanup, `CODE.md` only covers skills/agents/templates — check the code itself against the top-level `.github/copilot-instructions.md` "General Python Guidelines" too (e.g. `pathlib.Path` for filesystem ops instead of `os.path`/bare `open()`).
- Chorey's mode instructions require delegating change-set reading to an `Explore` subagent (thoroughness: medium) — that subagent exists but has **no terminal access**, so it cannot run `git diff`/`git show` and substitutes file-inspection guesses for the real diff (it announces the limitation, but its guessed sections read like fact). Use it for on-disk reads, repo-wide greps, and link checks only; always read the diff yourself with `git --no-pager diff --cached`.
- `git --no-pager diff` on a large change set overruns the terminal scrollback and silently drops the *beginning* of the output — the tail survives, so the loss is easy to miss. Redirect to a file (`> /tmp/x.txt`) and read it in ranges, or diff a subset of paths per invocation.
- PyYAML is not installed for `python3` in this environment (`ModuleNotFoundError: No module named 'yaml'`) — parse frontmatter with `re` rather than adding a dependency, whether for a one-off audit script or a permanent check (see `tools/src/modules/repo_consistency/frontmatter.py`); require *both* the opening and closing `---` delimiters — a file missing only the opening one (real bug found in `plugins/azure-platform/skills/search-ms-*`) still starts with a `key: value` line that a naive line-scan would treat as valid frontmatter.
- When auditing `docs/concepts/*.md` against `CONCEPT-FORMAT.md`, `grep '^## '` yields false positives from `##` headings inside fenced template blocks (0004's `## Completeness sweep`, 0005's `## <Task name> Workflow`) — read the surrounding lines before reporting a section-order violation. Two checks worth scripting: the `ARCHITECTURE.md` Summary cell is exactly `**Default:** {default} {summary}` concatenated from frontmatter, and `related` must be bidirectional in the same change (a record adding a link to an older record is the side that usually gets the return link right, so check the older record too) — neither is implemented yet; `tools/src/modules/repo_consistency/architecture_index.py` only checks each index row's id/title against its record's filename, `# ` heading, and frontmatter (falling back past ADRs 0001-0004, which have no frontmatter block at all).
- When reviewing a skill-retirement commit that lives on a worktree/branch not yet merged into `HARNESS_REPO_PATH`'s checked-out branch, a repo-wide grep for the retired skill's name can surface hits in a different plugin entirely (e.g. a generated-instructions template's "Available skills" list still naming a just-deleted skill) — that file is a separate change set; record it as a follow-up finding, never edit it into the current review.
- A ticket's "Verify section" can claim a *prior* ticket already introduced artifacts (e.g. "the VERIFY-<stack>.md and CHORE-<stack>.md templates introduced or resolved by #112") that the prior ticket's own comment shows were never actually created — check the referenced ticket's completion comment for its own listed gaps before assuming the claimed artifact exists; the current task's scope is unaffected when it doesn't (per-stack convention files remain user/setup-authored, read only if present).
- Invoking `python3 -m pytest` with multiple `plugins/atl/skills/<skill>/` paths in one command fails collection with "import file mismatch" whenever two sibling skills' `tests/` folders share a basename (e.g. `preflight-atl/tests/test_cli.py` vs `publish-page/tests/test_cli.py`) — neither has an `__init__.py` and no `--import-mode=importlib` is configured. Run each skill's suite as a separate `pytest` invocation and sum the pass counts instead of relying on the combined command's exit status.
- Chorey must never `git commit` its own applied-and-verified fix, even after VERIFY passes — leave it staged/uncommitted in the workspace for the caller (`to-commit`) to commit; if committed by mistake and not yet pushed, `git reset --soft HEAD~1` to uncommit while keeping the change.
- When a file already in the change set (touched by the current commit under review) also carries a stale reference to a *different*, earlier-deleted skill (e.g. an "Available skills" list edited for one skill's removal still names another skill deleted in a prior ticket), grep that same file for every previously-known-deleted skill name, not just the ones this commit deletes — fixing the adjacent stale entry is in-scope since the line is already being touched.
- When a test mocks a function that mutates its input list-of-dicts in place to add new keys (e.g. `render_diagrams` adding `filename`/`mmd_path`/`png_path` to each diagram dict), a bare no-op `MagicMock()` silently drops that mutation — give it a `side_effect` that performs the same in-place mutation, or downstream code reading those keys (`upload_diagrams`) raises `KeyError`.
- When an argparse subcommand builder function (`build_arg_parser`) needs a subparser variable whose subcommand name collides with a module-level imported function name (e.g. a `publish-adf` subparser named `publish` colliding with `from .pipeline import publish`), Python's per-function scoping makes this technically safe, but rename the local subparser variable anyway (e.g. `publish_adf`) — the shadow is confusing on re-read and risks a real bug the next time a new subcommand or import is added nearby.
- When Chorey's `BASELINE_COMMIT` equals the workspace's current `HEAD` (the normal case right after Codey/`to-commit` creates the checkpoint), the change set is that commit's own diff — use `git show --stat <sha>` (per `crew-review` Step 0), never `git diff <sha> HEAD`, which is empty and wrongly reads as "nothing to review".
- When reviewing a commit that extracts an agent's inline workflow into a new shared skill (e.g. a `crew-*-flow` skill), check the new sibling skill(s) for a verbatim-duplicated `## HARD RULES`/guardrail bullet carried over from each original agent file — `agent-skills.instructions.md`'s "shared procedure is invoked, not duplicated" applies, but when neither sibling is a natural owner, record it as a finding (needs a human/Codey decision on where the shared rule lives) rather than picking one arbitrarily. Also check the plugin's `README.md` for now-stale Components/dependency-diagram prose describing the old agent-owns-workflow shape — it's outside the diffed change set, so flag it as a follow-up finding rather than editing it.
- `/crew-select` skill is referenced (its **Resolve From Changed Files**/**Resolve From Task Text** actions) by `crew-review`, `to-chorey`, and `to-codey`, but `plugins/crew/skills/crew-select/` doesn't exist yet — a pre-existing forward reference, not a bug in whichever commit currently invokes it. Don't create the skill during a cleanup review (out of scope) and don't flag the missing target as a finding unless the change set under review is what introduced the reference.
- When scripting a repo-wide skill-invocation resolver (backticked `` `/name` `` pattern), scope the file scan to `SKILL.md`/`*.agent.md` only — `references/`, `templates/`, `assets/` siblings and `.crew/GOTCHAS.md` legitimately reuse the same backtick-slash shape for unrelated things (a page route example like `` `/monitoring` ``, a literal placeholder `` `/name` `` in a convention example) and read as false-positive dangling invocations otherwise. A genuinely dangling one does still turn up this way in real skill bodies (`` `/triage` `` in `manage-backlog/SKILL.md`, unresolved since the file was written) — fix it when found rather than special-casing it away.
- CODE.md's skill-invocation convention (``Run `/name` skill **Section**``) already varies across this plugin's own files on the apostrophe after the skill name (`` `/crew-select` skill `` vs. `` `/crew-review`' skill ``) — when a reviewed line also tacks on filler like "skill's ... action", trim it to the plain `` `/name` skill **Section** `` form (matching the majority pattern in `to-chorey`/`to-codey`) rather than leaving the extra words or picking a third variant.
- When a TEST_PLAN.md Feature bundles isolated-fixture scenarios with a "current repository" real-data scenario (e.g. `tools/tests/unit/repo_consistency/`), a second test class for the real-data scenario can drift onto an invented docstring like `"""Feature: Repository Consistency Check (Real Repo)"""` that names no actual TEST_PLAN.md heading — `copilot-instructions.md`'s "Test class docstring → Feature name... keep both sides in sync" means every class in the file must quote the *same* real Feature heading the scenario is listed under, even when split across multiple classes.
